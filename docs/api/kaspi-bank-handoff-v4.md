# DOS — Kaspi: пополнение баланса водителя

Версия 4, 19 октября 2026 года. Основание: «Протокол_взаимодействия_онлайн_новый_.pdf», предоставленный заказчиком.

**Статус реализации:** обработчик `check`/`pay` и возврат ФИО и телефона в `fields` реализованы. Документ описывает контракт DOS по предоставленному протоколу. Для банковского подключения остаются согласование настроек с Kaspi и проверка отдельного тестового счёта; наличие документа не означает включение доступа с IP банка.

## 1. Адрес сервиса и формат обмена

`GET https://89.126.200.51/api/v1/payments/kaspi`

Один адрес для команд `check` и `pay`. HTTPS, параметры в query string, без тела запроса. Ответ JSON, UTF-8, `Cache-Control: no-store`. Предельное время ответа по протоколу банка — 15 секунд. Перед банковским тестом проверить действительность TLS-сертификата и доступ с согласованных IP Kaspi.

Идентификатор `account` — телефон водителя DOS: 11 цифр, начинается с 7, без `+`, пробелов и скобок. Регулярное выражение: `^7[0-9]{10}$`.

Доступ без пользовательского JWT, только с подтверждённых IP Kaspi. Интеграция включается настройкой `KASPI_ENABLED=true` при заполненном `KASPI_ALLOWED_IPS`. В PDF указаны `194.187.247.152`, `194.187.245.108`, `197.187.244.108`; актуальность всех трёх адресов, включая третий, необходимо подтвердить у банка.

## 2. Сценарий для водителя

1. Водитель вводит свой зарегистрированный в DOS телефон в интерфейсе Kaspi.
2. Kaspi отправляет DOS `command=check` с этим телефоном.
3. DOS проверяет наличие доступного водителя: тип driver, пройдена верификация, пользователь не заблокирован, валюта баланса KZT или RUB, заполнены отдельные поля фамилии и имени.
4. При успехе DOS возвращает `result=0` и данные водителя в `fields`. Kaspi показывает фамилию, имя, отчество и телефон, после чего предлагает ввести сумму пополнения.
5. Водитель вводит сумму в Kaspi. Kaspi передаёт фактическую сумму в KZT в запросе `command=pay`.
6. DOS атомарно зачисляет платёж и возвращает `result=0` только после фиксации в БД.

По этому сценарию сумма вводится **после проверки номера в Kaspi**. Значение `sum` в `check` фиктивное и не является суммой, выбранной водителем. Сценарий выставления счёта из профиля DOS данным PDF не описан. Текущая заявка на пополнение из профиля сохраняется в DOS и сама по себе не отправляет счёт в Kaspi.

## 3. Проверка номера: запрос и успешный ответ

Все персональные данные и идентификаторы в примерах демонстрационные.

```http
GET /api/v1/payments/kaspi?command=check&txn_id=123456789012345677&account=77010000000&sum=200.00
Host: 89.126.200.51
Accept: application/json
```

Успешный ответ DOS:

```json
{
  "txn_id": "123456789012345677",
  "result": 0,
  "comment": "OK",
  "fields": {
    "field1": { "@name": "full_name", "#text": "Иванов Иван Иванович" },
    "field2": { "@name": "phone", "#text": "+77010000000" }
  }
}
```

Структура `fields` соответствует приложенному PDF. Названия `full_name`, `phone` — предлагаемое DOS отображение; их и подписи на экране необходимо согласовать с Kaspi. `full_name` — полное ФИО водителя одной строкой (без сокращений), `phone` — зарегистрированный телефон водителя DOS, а не произвольный номер плательщика.

DOS хранит фамилию, имя и отчество раздельно: `users.last_name`, `users.first_name`, `users.middle_name`. Водитель заполняет их при регистрации или в личных данных профиля. Изменение ФИО переводит профиль на повторную проверку администратором и отключает выход на линию до одобрения. Старое общее поле `users.name` автоматически не разделяется. Если фамилия или имя отсутствуют, `check` возвращает `result=1` без персональных данных. В `full_name` передаётся полное ФИО одной строкой: фамилия, имя, отчество через пробел. При отсутствии отчества передаются фамилия и имя без лишнего пробела. Подпись поля в интерфейсе Kaspi: «ФИО Водителя», например «ФИО Водителя: Иванов Иван Иванович».

Неизвестный или недоступный водитель — без персональных данных:

```json
{"txn_id":"123456789012345677","result":1,"comment":"Account not found or unavailable"}
```

Успешный `check` не резервирует сумму и не меняет баланс. `prv_txn_id` в ответе проверки отсутствует.

## 4. Оплата: запрос и ответ

```http
GET /api/v1/payments/kaspi?command=pay&txn_id=123456789012345678&txn_date=20261019140000&account=77010000000&sum=5000.00
Host: 89.126.200.51
Accept: application/json
```

```json
{
  "txn_id": "123456789012345678",
  "prv_txn_id": "2016",
  "result": 0,
  "sum": "5000.00",
  "comment": "OK"
}
```

Здесь `5000.00` — именно сумма в тенге, введённая водителем в Kaspi. ФИО не требуется передавать обратно в запросе `pay`: DOS определяет водителя по `account`. `prv_txn_id` генерируется DOS, пример `2016` условный. Повтор того же платежа возвращает исходный ответ без повторного зачисления.

## 5. Параметры

| Поле | Требование |
|---|---|
| command | Обязательно, `check` или `pay` |
| txn_id | Обязательно, строка из 1–18 цифр; у check и pay разные идентификаторы |
| account | Обязательно, телефон по шаблону `^7[0-9]{10}$` |
| sum | Обязательно; строка с точкой и двумя десятичными знаками, до 9 999 999 999.99 KZT; в check игнорируется, в pay строго больше нуля |
| txn_date | Обязательно для pay, существующая дата `YYYYMMDDhhmmss`; часовой пояс согласовать с Kaspi |

В JSON DOS сейчас возвращает `sum` строкой и `result` числом. В PDF приведён также пример числового `sum`; согласовать с Kaspi при подключении. Идентификаторы передаются строками для сохранения всех цифр. Дополнительные query-поля `data1…dataN` в этом сценарии не используются и текущим контрактом DOS не принимаются.

Пополнение принимается в KZT. Для баланса RUB зачисление пересчитывается по курсу города на момент подтверждения; банковский ответ сохраняет исходную сумму KZT. Например, при курсе 7 KZT за RUB: 1000 KZT = 142,86 RUB. Повтор платежа курс не пересчитывает.

## 6. Коды результата и ошибки

| result | Значение | Поведение DOS |
|---|---|---|
| 0 | Счёт найден / платёж выполнен | Успешный check либо зафиксированный pay |
| 1 | Абонент/счёт/заказ не найден | Нет доступного проверенного водителя с таким телефоном |
| 2 | Заказ отменён | Предусмотрено протоколом; при пополнении DOS не используется |
| 3 | Заказ уже оплачен | Предусмотрено протоколом; повтор успешного pay DOS возвращает 0 |
| 4 | Платёж в обработке | Предусмотрено протоколом; текущий синхронный обработчик не возвращает |
| 5 | Другая ошибка провайдера | Некорректная календарная дата, неположительная сумма, конфликт параметров txn_id |

Пример отказа при конфликте повторного платежа:

```json
{"txn_id":"123456789012345678","result":5,"comment":"Transaction parameters conflict"}
```

Бизнес-ответы протокола возвращаются с HTTP 200. Неверный синтаксис параметров — HTTP 400 с конвертом ошибок DOS; выключенная интеграция или запрещённый IP — HTTP 403. Инфраструктурная ошибка может дать HTTP 5xx или таймаут: нельзя считать её подтверждением оплаты. При неизвестном результате повторять исходный pay с теми же параметрами и txn_id.

Одинаковые `txn_id`, `account`, `sum`, `txn_date` не создают второго платежа. Изменённые параметры при том же txn_id дают result=5. Дата `txn_date` используется для бухгалтерской сверки, время обработки хранится отдельно.

## 7. Тестовые параметры и приёмка

**Рабочий тестовый номер в рамках подготовки документа не создан и не проверен.** `77010000000` — пример формата, он не является выданным тестовым счётом. Перед тестированием DOS должен предоставить Kaspi отдельный номер проверенного тестового водителя с заполненным ФИО, валютой и начальным балансом; неизвестный номер также нужно подтвердить как отсутствующий. Реальные персональные данные не включать в общедоступную документацию.

Параметры примеров: check txn_id `123456789012345677`, фиктивная sum `200.00`; pay txn_id `123456789012345678`, сумма `5000.00` KZT. В новом независимом тесте использовать новый pay txn_id и актуальную txn_date; при проверке повтора сохранять все исходные параметры. Сумму реального банковского теста согласовать отдельно.

Приёмка: существующий номер и ФИО на экране Kaspi; отсутствующий/заблокированный номер; сумма вводится после check; успешный pay и изменение баланса; повтор и конкурентный дубликат без второго зачисления; конфликт суммы; неверная дата; сверка по txn_date; недопустимый IP. Проверить возврат fields и отображение двух полей: «ФИО Водителя» одной строкой и телефона в интерфейсе Kaspi.

Для банковского запуска согласовать отображение fields, формат sum в JSON, часовой пояс, IP банка и отдельный тестовый счёт. Машинный контракт `kaspi-online.openapi.yaml` включает fields. Проверки DOS выполнены на изолированной тестовой БД; они не заменяют совместную приёмку с Kaspi.
