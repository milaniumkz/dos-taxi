# Kaspi: API пополнения баланса водителя

Источник: предоставленный документ «Протокол взаимодействия (онлайн)», файл `2322784556.193654783976931965.1.3.pdf` из переписки. Реализован описанный в нём HTTPS GET протокол `check`/`pay` с JSON UTF-8 ответами. Данные банковской карты не передаются: клиент оплачивает в Kaspi, банк сообщает о платеже нашему API.

## Endpoint для передачи банку

`GET https://89.126.200.51/api/v1/payments/kaspi`

По указанию заказчика указан IP сервера. HTTPS по IP проверен 7 октября 2026 из внешнего GitHub Actions runner с включённой проверкой сертификата: `/api/v1/health/ready` вернул HTTP 200, база данных, Redis и хранилище доступны. Установлен сертификат Let's Encrypt с IP `89.126.200.51` в Subject Alternative Name. Для короткоживущего IP сертификата включено автоматическое продление: systemd timer проверяет его каждые 12 часов и перезагружает Nginx после проверки конфигурации. Тестовое продление через ACME staging выполнено успешно.

[Проверка настройки HTTPS](https://github.com/milaniumkz/dos-taxi/actions/runs/37611085895). Доступ по прежнему доменному имени сохранён. Сам Kaspi endpoint остаётся выключенным до согласования и настройки разрешённых IP банка.

Один endpoint обслуживает обе команды. Метод GET, тело запроса отсутствует; все поля передаются в query string. Ответ HTTP 200 с JSON и `Cache-Control: no-store`. Таймаут банка — 15 секунд. TLS и ограничение IP обеспечиваются reverse proxy и API. Endpoint не требует пользовательский JWT, доступ разрешён только подтверждённым адресам Kaspi.

Идентификатор счёта `account` — телефон зарегистрированного, проверенного водителя DOS в городе с валютой KZT: **11 цифр, начинается с 7**, без плюса. Регулярное выражение для банка: `^7[0-9]{10}$`. Заблокированным пользователям пополнение недоступно.

## Полные запросы

Все номера ниже демонстрационные. Для теста банк должен получить номер отдельного тестового водителя.

### Проверка счёта

```http
GET /api/v1/payments/kaspi?command=check&txn_id=123456789012345677&account=77010000000&sum=200.00 HTTP/1.1
Host: 89.126.200.51
Accept: application/json
```

```json
{"txn_id":"123456789012345677","result":0,"comment":"OK"}
```

Сумма `sum` в `check` фиктивная, не влияет на баланс. `txn_id` проверки и платежа могут отличаться; успешная проверка не является резервированием или оплатой.

### Зачисление

```http
GET /api/v1/payments/kaspi?command=pay&txn_id=123456789012345678&txn_date=20261007140000&account=77010000000&sum=5000.00 HTTP/1.1
Host: 89.126.200.51
Accept: application/json
```

```json
{"txn_id":"123456789012345678","prv_txn_id":"2016","result":0,"sum":"5000.00","comment":"OK"}
```

`prv_txn_id` в примере условный. Реальный номер генерирует база данных DOS, он не связан с номером карты.

| Поле | Тип и ограничения | check | pay |
|---|---|---|---|
| command | `check` или `pay` | обязательно | обязательно |
| txn_id | строка из 1–18 цифр | обязательно | обязательно |
| account | строка `^7[0-9]{10}$` | обязательно | обязательно |
| sum | строка с точкой и двумя знаками после неё; KZT; максимум 9 999 999 999.99 | обязательно, игнорируется | обязательно, больше нуля |
| txn_date | строка из 14 цифр `YYYYMMDDhhmmss`, существующая календарная дата | не нужно | обязательно |

18-значные `txn_id` нельзя передавать через JavaScript `Number`: они сохраняются и возвращаются строками. `sum` возвращается строкой с двумя десятичными знаками, что сохраняет копейки. Это соответствует строковому описанию полей в документе; согласовать с банком тип поля JSON перед включением.

Дополнительные `data1…dataN` документ допускает, но в текущем контракте они не нужны и не принимаются. XML не используется: документ позволяет выбрать JSON или XML. Заголовок `X-Idempotency-Key` не нужен, уникальный ключ платежа — банковский `txn_id`.

## Ответы и повторные запросы

| result | Значение протокола | Применение в DOS |
|---|---|---|
| 0 | счёт найден / платёж выполнен | check либо успешный pay |
| 1 | счёт или заказ не найден | нет доступного проверенного водителя с таким телефоном |
| 2 | заказ отменён | не используется при пополнении баланса |
| 3 | заказ уже оплачен | не используется: повтор pay возвращает исходный успешный ответ |
| 4 | платёж в обработке | не используется при синхронном атомарном зачислении |
| 5 | другая ошибка провайдера | некорректная дата/сумма, конфликт параметров, временная ошибка БД |

Повторный `pay` с теми же `txn_id`, `account`, `sum`, `txn_date` возвращает прежний `prv_txn_id` и не меняет баланс. Другие параметры при том же `txn_id` дают `result=5`, без повторного зачисления. Конкурентные дубликаты сериализуются через PostgreSQL advisory lock. Баланс, запись пополнения и банковская транзакция сохраняются в одной транзакции БД. Если зачисление не зафиксировалось, вся операция откатывается; повторять нужно с исходным `txn_id`.

`txn_date` сохраняется отдельно как исходная **дата учёта банка**, `created_at` — время обработки DOS. Для сверки по отчётному периоду использовать `kaspi_transactions.txn_date`, а не время обработки. Перед запуском подтвердить часовой пояс `txn_date` у Kaspi. Пример SQL сверки:

```sql
SELECT txn_id, id AS prv_txn_id, account, amount, txn_date, created_at
FROM kaspi_transactions
WHERE txn_date >= '20261001000000' AND txn_date < '20261101000000'
ORDER BY txn_date, txn_id;
```

Пополнения отображаются в админке как подтверждённые с `invoice_provider=kaspi`; повторно подтверждать их вручную не нужно. При блокировке водителя повтор ранее успешного платежа всё равно возвращает исходный результат.

Некорректный синтаксис query даёт HTTP 400 с обычным конвертом ошибок DOS. Запрещённый источник или выключенная интеграция — HTTP 403. При `result=5` банк должен сохранить `txn_id` для сверки и повторного запроса, а не генерировать новый платеж.

## Подключение и параметры сервера

1. Применить миграции и развернуть проверенный код. Подтвердить HTTPS адрес `https://89.126.200.51/api/v1/payments/kaspi` в настройках банка. IP сертификат уже установлен и проверен; автоматическое продление должно оставаться включённым.
2. Получить от Kaspi идентификатор услуги/договора, актуальные IP источников, формат JSON `sum` и часовой пояс `txn_date`. В документе перечислены `194.187.247.152`, `194.187.245.108`, `197.187.244.108`; третий адрес отличается от остальных — подтвердить список у банка перед использованием.
3. Заполнить `KASPI_ALLOWED_IPS` подтверждёнными **отдельными IP** через запятую. Указать `TRUST_PROXY` только для фактических внутренних адресов/подсетей reverse proxy; API не должен быть доступен из интернета в обход proxy.
4. Передать Kaspi endpoint по IP, регулярное выражение account, эту документацию и номер тестового водителя. Провести check, pay, повтор pay, неизвестный номер, ошибочную дату, конкурентные дубликаты и сверку транзакций.
5. Включить `KASPI_ENABLED=true` после согласования. При отсутствии whitelist запуск с включённой интеграцией отклоняется. По умолчанию интеграция выключена.

Подпись/секрет запроса в предоставленном документе не описаны. Не добавляем выдуманное поле подписи; если банк требует его в актуальном контракте, адаптировать доступ до запуска. Не передавать PAN, CVV, срок действия карты или банковские секреты в этот endpoint.

OpenAPI контракт доступен в Swagger `/docs` и генерируемом `docs/api/openapi.json`; отдельный файл `kaspi-online.openapi.yaml` предназначен для передачи банку.
